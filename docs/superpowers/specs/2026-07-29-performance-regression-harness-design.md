# パフォーマンス退化検知ハーネス 設計書

日付: 2026-07-29
状態: 承認済み（ブレインストーミング経由）

## 背景と動機

このリポジトリには `profile.lua` による計装があるが、その値を読むのは人間の仕事に
なっていた。実際、直近の性能調査では利用者にプロファイルログを収集させ、それを
貼ってもらって初めて三つの問題（cold ラベルの誤り、ブロックフォールバック時の
二重取得、拒否理由の欠落）が判明した。これは順序が逆である。計測環境は開発側に
あり、開発側と CI が回すべきものである。

さらに、これまでの計測自体に方法論上の欠陥があった。すべて n=1 ないし n=2 の
単発測定であり、同一の `extract:cold` が 4012ms と 580ms を示していたにもかかわらず
「568ms」という単一の値を事実として報告していた。統計的な根拠がない。

本設計は、この二点（誰が測るか / どう測るか）をまとめて解決する。

## 目的

**利用者が計測作業を一切行わなくても、性能退化が自動的に検知される状態にする。**

副次的に、開発側が性能について語るときの数字を、単発の観測ではなく反復に基づく
統計値にする。

## 判定方針

利用者との合意により、pass/fail の主軸は **構造不変量** とし、実時間は **参考値**
として記録・報告する。

理由は、これまで実際に発生した退化がいずれも「N% 遅くなった」ではなく
「往復が一回増えた」「キャッシュが効かなくなった」という構造の変化だったこと、
および CI ランナーの実時間が 2〜3 倍ぶれるためである。

### 構造不変量（pass/fail の対象）

以下はワークロードの規模と無関係に成立すべき性質であり、プロファイルの
スパン列から判定する。

1. `ee` 一回につき `locate:ok` 一回、`extract:*` 一回。二回以上なら二重取得の再発。
2. 同一ヘッダの二つめ以降のシンボルは `extract:warm`。`extract:cold` なら
   attach キャッシュが機能していない。
3. ブロックフォールバック時、追加の `locate` / `extract` は発生しない
   （取得済みの本体を引き渡す設計が壊れていないこと）。
4. 編集中のファイル内に定義があるシンボルは `extract:cold` にならない。
5. 健全な clangd に対するマクロ展開は `macro:tweak` 一回で完了し、
   `macro:hover` にフォールバックしない。

### 実時間（参考値、限定的な失敗条件）

シナリオごとに p50 を `tests/bench_baseline.json` と比較し、常に報告する。
失敗させるのは次の条件を満たす場合のみとする。

```
p50 > baseline_p50 + max(3 × noise_floor, baseline_p50 × 0.25)
```

`noise_floor` はハーネス自身が毎回測定する（後述）。閾値を固定値ではなく
実測ノイズから導出するのは、CI ランナーの性能差を吸収するためである。

## 計測方法論

以下は本ハーネスが守るべき規約であり、実装の中核である。

1. **単発測定を禁止する。** シナリオごとに既定 15 反復。先頭 3 反復は
   ウォームアップとして破棄する（clangd のインデックス整備、OS のページキャッシュ）。
2. **平均値を使わない。** レイテンシ分布は右に裾を引くため、p50 と p90、
   および MAD（中央絶対偏差）を報告する。mean ± sd は誤導する。
3. **cold と warm を別母集団として測る。** 両者を混ぜた統計は無意味である。
   cold の反復は「同形の別ヘッダ h1..hN をそれぞれ一度だけ触る」ことで得る。
   clangd を反復ごとに再起動するより安価で、cold の意味論は同一である。
4. **ノイズフロアを必ず測定・報告する。** 同一シナリオを二つの独立した母集団として
   実行し、その p50 の差をハーネス自身の再現性とする。この値を超えない差は
   「差がない」と扱う。ノイズフロアが退化閾値を上回る場合、その回の時間計測は
   信頼できないものとして報告に明記する。
5. **環境を固定する。** clangd のバージョン、フィクスチャ、コンパイルフラグを
   ピン留めする。`compile_commands.json` は絶対パスを含むためコミットせず、
   ベンチ実行時に生成する。
6. **実 clangd のみを使う。** 偽サーバは用いない（利用者の判断）。フィクスチャは
   小規模だが、cold の測定に意味を持たせるためヘッダ連鎖に十分な重さを持たせる。

## 構成

- `tests/lib/bench.lua` — 統計（p50 / p90 / MAD）、反復ランナー、ノイズフロア測定、
  プロファイルスパン列の収集と検査
- `tests/fixtures/bench/gen.lua` — フィクスチャ生成。重ヘッダ連鎖 h1..hN、
  それらを使う main.c、マクロ、`compile_commands.json`
- `tests/bench_spec.lua` — シナリオ定義、構造アサーション、統計レポート、
  ベースライン比較
- `tests/bench_baseline.json` — コミットする基準値。シナリオごとの p50 と、
  記録時のノイズフロアを含む
- CI: 既存の fast suite とは別ジョブ。clangd のリリース版を取得して実行する。
  push 時のみ（PR では fast suite だけを回す）

## シナリオ

各シナリオは独立した母集団として測定する。

- `expand:cold` — 未オープンのヘッダにある定義をブロック展開する
- `expand:warm` — 既に attach 済みのヘッダから別のシンボルをブロック展開する
- `inline:function` — 関数のインライン置換
- `inline:macro` — マクロの in-place 展開（ExpandMacro tweak 経路）
- `expand:same-file` — 編集中のファイル内にある定義を展開する（不変量 4 の検証）

## 却下した代替案

- **偽 LSP サーバを主軸にする案**: 決定的で高速だが、利用者が実 clangd での
  検証を選択した。
- **実カーネルを CI で回す案**: 本番相当の重さだが、tarball 取得に加えて
  m4 / bison / flex / bc / libelf のソースビルドが必要で初回 10 分超。
  push ごとには回せない。手元での確認手段としては引き続き用いる。
- **実時間のしきい値を主軸にする案**: 直感的だが CI で不安定であり、
  実際に起きた退化の大半を捉えられない。

## 受け入れ条件

- `tests/bench_spec.lua` が実 clangd に対して緑になり、五つの構造不変量すべてを
  検証していること。
- 本ハーネスが、今日修正した三つの問題（cold ラベル誤り、二重取得、
  detach による preamble 再構築）を、修正前のコードに対して**赤**として
  検出できること。これは実装時に revert して確認する。
- 時間レポートに p50 / p90 / MAD とノイズフロアが含まれること。
- CI に専用ジョブが存在し、利用者側の操作を一切必要としないこと。

## テスト実行方法

```sh
nvim --headless --clean -u NONE -c "luafile tests/bench_spec.lua" -c "qa!"
```

環境変数で反復数などを調整できるようにする（`IE_BENCH_REPS` 等）。
