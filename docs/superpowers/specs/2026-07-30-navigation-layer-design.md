# ナビゲーション層（callers・定義ジャンプ・履歴）設計

日付: 2026-07-30
状態: 承認済み（ブレインストーミングセッションでセクションごとに承認）

## 背景と目的

このプラグインの現機能はすべて「下り・その場」である: 呼び出しの下に定義を差し込み、
その中でさらに展開する。巨大コードベース（本命はカーネル）を読む際の残る痛点として
ユーザーが挙げたのは #ifdef の生死、上り方向、データの出所、迷子の4点で、最初に作る
ものとして「上り方向（callers）」が選ばれた。あわせて「ジャンプ機能は絶対に必要」と
の要望があり、両者は同じ基盤（ビュー切替と履歴）の上に載るため、1つのナビゲーション
層として設計する。

導入後の移動の全体像:

- 下り・その場: 展開・インライン置換（既存のまま）
- 下り・移動: 定義ジャンプ（新規、ビュー内 `gd`）
- 上り・移動: callers picker からの切替（新規、`<leader>eu`）
- 履歴: 戻る/進む（新規、ビュー内 `<C-o>` / `<C-i>`）

方針決定: 上りは「差し込み」ではなく「移動」。caller の文脈は関数全体を読みたい
ため、スニペットの差し込みより、そのファイルの読み取りビューへ切り替える方が読み方
として自然である（ユーザー選択）。

## 不採用にした代替案

- ネイティブ jumplist / tagstack に乗せる案: ビューは `bufhidden=wipe` の nofile
  バッファであり、ネイティブ jumplist は wipe されたバッファへ戻れない。戻れたと
  しても展開状態は消えている。「戻る」が読解セッションで意味を持つには展開状態ごと
  戻る必要があり、それはネイティブ機構の外にある。
- picker からカーソルジャンプのみの案: 「読むのは常にビューの中」という思想から
  外れ、展開機能と合成できない。

## アーキテクチャ

新モジュール `lua/inline-explorer/trail.lua`。中心プリミティブは1つ:

```lua
trail.goto_location(loc)  -- loc = { uri, range }（解決済みの位置）
```

（設計時は `nav.lua` としていたが、既存の `nav.lua`（ビュー内のブロック間移動
next/prev/list/breadcrumb）と名前が衝突するため `trail.lua` に改名。既存 nav には
手を入れない。）

動作: 現在のビュー状態（バッファ、カーソル）を履歴スタックに積み、対象ファイルの
読み取りビューへウィンドウを切り替える。対象ファイルのビューバッファが既に存在すれ
ば**バッファを**再利用（その展開状態が生きたまま表示される）、なければ新規作成。

再利用の意味を明確にする: スタックの実体は (バッファ, カーソル位置) の列であり、
同じバッファが複数回現れてよい。「再利用」はバッファの使い回しであって、スタック上
の過去エントリへの巻き戻しではない。また、戻った状態から新しいナビゲーションを行う
と前方（forward）履歴は破棄する — 通常のブラウザ/jumplist と同じ規則。

既存モジュールへの変更は最小限に留める。`resolver` / `view` / `expander` には手を
入れず、nav はそれらの利用者として上に載る。新しい LSP 面は callHierarchy のみ。

### ビューの生存管理

現行の `bufhidden=wipe` は「ビューは常に1枚」の前提に基づく。nav 導入後:

- スタックに積まれている間は `bufhidden=hide`
- スタックから追い出されたとき（深さ上限超過、または `InlineExplorerClose`）に wipe
- 深さ上限は既定 8（`trail._stack_n`、テストから縮められるモジュールフィールド。
  resolver の attach cache と同じ流儀）

### 履歴

双方向スタック（カーソル位置つき）。戻るときは積んであるバッファをそのまま表示する
だけなので、展開状態・fold・undo 履歴が完全に生きて戻る。スナップショットや
シリアライズはしない — 消さなければ復元は要らない。

## caller picker

### 取得

1. 一次: LSP `textDocument/prepareCallHierarchy` → `callHierarchy/incomingCalls`
2. フォールバック（0件または未対応時のみ）: `rg`（無ければ `grep`）で識別子を検索し、
   tree-sitter で「call_expression の callee か」を照合

各行に出所ラベル `[lsp]` / `[grep]` を付け、どちらの結果かを隠さない。v1 では混合
表示はしない（複雑さの割に利得不明。使ってから判断）。

### 不完全性の明示

インデックス構築中の clangd は不完全な結果を黙って返す。対策:

- picker タイトルに件数と出所を常時表示（例: `callers of foo — 12 [lsp]`）
- LSP・grep とも0件のときは「callers が見つからない（インデックス未完の可能性
  あり）」を通知し、空の picker は開かない

「0件 = 呼ばれていない」と読ませないこと。real-source ハーネスで潰し続けた偽グリーン
と同型の罠であり、UI でも同じ規律を適用する。

### 表示と選択

- `vim.ui.select` ベース。専用フロートは作らない（dressing.nvim / telescope の
  差し替えがあればそのまま恩恵を受ける）
- 1行 = `関数名  file:line  │ 呼び出し行テキスト（trim 済み）`
- ソート: ファイル内は行順、ファイル間はファイル名順
- 選択後: `trail.goto_location(呼び出し位置)`。カーソルは呼び出し行

### キー

ビュー内 `<leader>eu`。ソースバッファからも使用可（ビュー未オープンなら開いてから）。

## 定義ジャンプ

ビュー内 `gd`。カーソル下の識別子を `resolver.locate`（既存。キャッシュ済み・
local-first 化済みで数ms）で解決し、`trail.goto_location`。展開との違いは「差し込む」
か「移動する」かだけで、解決経路は同一。ソースバッファの `gd` には触らない。

## 履歴キーとコマンド

- ビュー内 `<C-o>` / `<C-i>`: ナビスタックの戻る/進む。ネイティブと同じ指の動き
- スタック底で戻ろうとしたら通知のみ（何もしない）
- `InlineExplorerTrail`: スタック全体を location list へ（breadcrumb の縦方向版）

## エラー処理

- `prepareCallHierarchy` 失敗/タイムアウト → grep フォールバック。両方空なら通知
  して何もしない
- ジャンプ先ファイルが読めない → 通知して現ビュー維持。スタックは汚さない
- LSP タイムアウトは既存 `once_with_timeout` の流儀を踏襲（黙って待たせない、縮退を
  明示する）

## テスト方針

- trail スタック単体: push / back / forward / 上限追い出し / wipe タイミング。
  時間ではなくカウンタで検証する（このプロジェクトの計測規律）
- picker: `vim.ui.select` をスタブして選択を注入
- callHierarchy: resolver_spec の in-process 偽サーバに `prepareCallHierarchy` /
  `incomingCalls` を追加。正常系 / 0件→grep フォールバック / タイムアウトの3系
- 実カーネル統合: `real_kernel_spec` に1節追加。`kernel/sched/core.c` の実関数で
  incomingCalls が非空、切替→戻るで展開状態が保存されていることを確認（カーネルが
  本命ワークロードである原則）
- grep フォールバックの曖昧性: 「同名 static が複数ファイルにある」フィクスチャを
  1本（zlib ハーネスで学んだ多重定義の罠と同型）

## スコープ外（今回作らない）

- #ifdef の生死表示（ハーネスの生存行検出の流用先として有望だが別スペック）
- データフロー追跡（フィールドの書き込み元一覧）
- 探索セッションの保存/復元
- caller スニペットの差し込み表示・2段構え UI
- picker の LSP/grep 混合表示
