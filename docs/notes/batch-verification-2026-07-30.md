### [high/structure] macro.lua's private parse copy drifted: csrc.parse gained a cache, the copy did not, so macro splice re-parses the whole caller
場所: `lua/inline-explorer/macro.lua:11`

検証者の結論: Every claim re-derived and confirmed. macro.lua:11-13 carries the verbatim pre-cache parse body and requires csrc nowhere; csrc.lua:23-48 has the text-keyed LRU cache whose comment names only the three substitute/canalyze sites. The same smart-inline keypress feeds both paths: inliner.lua:32 builds src, line 34 parses it cached via substitute.call_name_at (C.parse, substitute.lua:91), line 117 re-parses it uncached via macro.replace_in_src (macro.lua:96). Timing reproduced headless on kernel fair.c (13,683 lines): cached hit 0.0003 ms vs macro-style bare parse 33.70 ms (cold 33.76 ms; a second bare parse costs 32.84 ms, so get_string_parser does not memoize) — far above the ~1ms triviality threshold. No csrc.parse calls occur between the two sites, so the cache entry for the same interned string is live and the suggested one-line fix (require csrc) would be a free hit. The drift is also documented-against: docs/notes/survey-dead-and-duplication.md section 1 quotes csrc.parse at commit 27d4f95 as the identical bare body, proving the cache landed after the survey and the copy did not follow. Behavior is identical (same tree, just slower), so this is performance/maintenance rather than correctness, but by the codebase's own standard — the cache exists precisely to remove ~30-60ms parses from this keypress — the finding stands as filed.

提案: Replace macro.lua's local parse/sb/eb/scol with require("inline-explorer.csrc") — replace_in_src then gets the cache hit for free on the macro path of the same keypress.
